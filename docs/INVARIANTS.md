# Project Rush — Core System Invariants

These invariants define the correctness contract for Project Rush V1.1.

They are intentionally written so they can later be mapped to automated tests, concurrency tests, and failure-injection scenarios.

---

## INV-1: Lifecycle Eligibility

Every campaign selected by Rush must be `ACTIVE` at decision time.

```text
Status(Campaign) == ACTIVE
```

A campaign in `DRAFT`, `SCHEDULED`, `PAUSED`, `COMPLETED`, or `CANCELLED` must never be returned in an ad decision.

---

## INV-2: Temporal Eligibility

A campaign may only be selected inside its configured delivery window.

```text
Campaign.start_time <= T_decision < Campaign.end_time
```

A campaign must never be selected before its configured start time or at/after its configured end time.

---

## INV-3: Targeting Validity

Every selected campaign must satisfy all targeting constraints configured for the current request.

Examples may include:

```text
region
device
subscription_tier
content_category
```

If any configured hard targeting rule fails, the campaign is ineligible for that ad opportunity.

---

## INV-4: Frequency-Cap Safety

A viewer must never receive a campaign beyond its configured frequency policy.

Example:

```text
frequency_cap = 3 per viewer per day

viewer has already received campaign 3 times
→ campaign must be rejected
```

Frequency-cap enforcement is a hard constraint.

---

## INV-5: Hard Capacity Bound — V1.1

For every campaign:

```text
CommittedAllocations(campaign)
    <=
ConfiguredCapacity(campaign)
```

This invariant must remain true under concurrent decision requests.

Rush must never issue more committed allocations than the campaign allows.

---

## INV-6: Pod Duration Safety

For every returned ad pod:

```text
Σ Duration(creative) <= Opportunity.duration
```

Example:

```text
30-second opportunity

15 + 10 + 5 = valid
20 + 15     = invalid
```

An under-filled pod is valid.

If no eligible campaign/creative combination exists, Rush may return:

```json
{
  "status": "NO_FILL",
  "ads": []
}
```

This is a valid successful decision outcome.

Rush must never violate a hard constraint merely to fill the remaining duration.

---

## INV-7: Competitive Exclusion

For every pair of campaigns selected into the same pod:

```text
Conflicts(campaign_a, campaign_b) == false
```

This rule only applies where a competitive-exclusion relationship has been configured.

Example:

```text
Coca-Cola ↔ Pepsi
```

If configured as competitors, they must not coexist in the same ad pod.

---

## INV-8: Creative Validity

Every selected creative must:

- belong to an eligible campaign;
- be valid for the current opportunity;
- fit within the remaining pod duration;
- satisfy all applicable creative-level constraints.

The final ad pod contains **Creatives**, not Campaign objects.

---

## INV-9: V1.1 Allocation Accounting

V1.1 uses **decision-level allocation accounting**.

Once Rush successfully commits and returns an ad decision containing a campaign, the corresponding campaign capacity is permanently consumed.

Playback failure does not reclaim that capacity in V1.1.

Rush knowingly accepts:

> **under-delivery / wasted inventory**

This is an intentional V1.1 tradeoff in favor of simple and conservative hard-cap correctness.

V1.2 will introduce temporary reservations and asynchronous reconciliation.

---

## INV-10: Idempotent Allocation

Every decision request must contain a deterministic:

```text
request_id
```

or equivalent idempotency key generated by the caller.

Within the configured idempotency retention window:

- repeated identical requests must return the same decision;
- concurrent duplicates must not create multiple allocations;
- campaign capacity must be consumed at most once;
- the original decision payload must remain stable;
- reuse of the same request ID with a materially different request payload is invalid.

---

## INV-11: Hard Constraints Dominate Soft Optimization

Soft ranking signals may only influence selection among campaigns that have already passed every hard constraint.

Examples of soft signals:

```text
priority
pacing
business value
delivery urgency
```

No soft preference may override:

```text
lifecycle
time window
targeting
frequency
capacity
duration
competitive exclusion
```

---

## V1.1 Correctness Philosophy

Rush V1.1 prioritizes:

```text
correctness
consistency
hard-cap safety
predictable behavior
```

over perfect utilization.

Where uncertainty exists, V1.1 prefers to waste inventory rather than risk over-allocation.

---

## Future V1.2 Changes

V1.2 is expected to introduce:

```text
temporary reservations
impression confirmation
Kafka-based reconciliation
reservation expiry
safe capacity reclamation
duplicate event handling
late event handling
```

Those features will extend the accounting model without weakening the V1.1 hard-cap guarantees.
